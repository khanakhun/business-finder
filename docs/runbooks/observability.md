# Observability (BF-061)

Metrics, logs and traces for production, self-hosted on VPS-1 next to the application, as their own compose
project (`bf-obs`, `infra/compose/docker-compose.observability.yml`). **Decision:** self-hosted rather than Grafana
Cloud — no per-series cost, no data leaving the host, one more stack to run (≈ 1.5 CPU / 4 GB at most by the limits;
typical use well under the 10% CPU budget). LLM traces stay with **Langfuse Cloud** (already wired:
`LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY`; spans only, prompts and outputs only with `AI_TRACE_CONTENT=true`,
which stays off in production — no prospect data beyond ids).

| Part | What | Retention |
|---|---|---|
| Prometheus v3.13 (LTS) | scrapes api, worker, intel (Docker DNS: every replica), Caddy (:2020), node_exporter (+ the backup textfile), cAdvisor, Postgres, Valkey, blackbox probes; evaluates `infra/observability/alerts/*.rules.yml` | 30 days |
| Alertmanager | routes by severity: page → e-mail + chat (hourly repeat), warn → e-mail, ticket → daily e-mail | — |
| Grafana | `grafana.<domain>` through Caddy; dashboards from `infra/observability/dashboards` (generated by `scripts/infra/gen-dashboards.mjs`) | — |
| Loki | container logs via Alloy (Docker API through a read-only socket proxy), with e-mail addresses and bearer tokens masked on top of the loggers' own redaction | 30 days |
| Tempo | OTLP from the applications via Alloy; tail sampling keeps every trace with an error and 10% of the rest | 14 days |

## 1. Install and update

1. DNS: `grafana.<domain>` → VPS-1 (Caddy already routes it).
2. On the server: `/opt/bf/observability/` holds `docker-compose.observability.yml` and, next to it, the repository's
   `infra/observability/` as `../observability` (copy both from the release you deploy; they change rarely).
3. Secrets in `/opt/bf/observability/secrets/` (mode 600): `grafana_admin_password`, `alert_smtp_password`,
   `alert_webhook_url` (a Slack incoming webhook or a Telegram relay URL), `pg_monitor_password`.
4. In `/opt/bf/.env`: `ALERT_EMAIL_TO`, `ALERT_EMAIL_FROM`, `ALERT_SMTP_SMARTHOST` (`host:587`),
   `ALERT_SMTP_USERNAME`, `CANARY_URL` (the canary preview, see slos.md).
5. `cd /opt/bf/observability && docker compose -p bf-obs -f docker-compose.observability.yml --env-file ../.env up -d`
   (after the application stack: it joins `bf_edge`, `bf_data` and the `bf_metrics-textfile` volume).
6. In `app.env`: `OTEL_EXPORTER_OTLP_ENDPOINT=http://alloy:4318` (then redeploy), so traces reach Tempo.
7. Check: Grafana → *Business Finder* folder; Prometheus targets all up (`ScrapeTargetDown` stays quiet).

Dashboards: change `scripts/infra/gen-dashboards.mjs`, run it (then `pnpm exec biome check --write
infra/observability/dashboards`), commit, copy. Alerts: edit the rules, `promtool check rules`, then
`curl -X POST http://prometheus:9090/-/reload` from a container on the `obs` network (or restart Prometheus).

## 2. The Postgres monitoring role

Once, as the owner role:

```sql
CREATE ROLE bf_monitor LOGIN PASSWORD '<pg_monitor_password>';
GRANT pg_monitor TO bf_monitor;
GRANT CONNECT ON DATABASE <db> TO bf_monitor;
```

## 3. Not here (yet)

- **Sentry** (error tracking with releases and source maps): not wired — no SDK is installed in web, api, worker or
  sites. Errors are in Loki (by `service`, `level`) and every failing trace is kept in Tempo. Adding Sentry is a
  follow-up: the SDKs, the DSNs in config, `connect-src` for the browser, and source map upload in `release.yml`.
- **Per-page renderer metrics**: the renderer exports none; its SLO is synthetic (slos.md).
