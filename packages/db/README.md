# @bf/db

Drizzle ORM over postgres.js: client, custom PostgreSQL types, ambient transactions, migrations and seeds.
Only `apps/api` (HTTP + worker) writes; `apps/sites` connects with `createDb({ readOnly: true })` and the
`bf_sites_ro` role (ADR-0004).

## Commands

| Command | What it does |
|---|---|
| `pnpm db:migrate` | Apply pending migrations to `DATABASE_URL` (re-running is a no-op). Never runs on app startup. |
| `pnpm db:generate --name <snake_name>` | Generate a migration from `src/schema` changes. Add `--custom` for a hand-written SQL file. |
| `pnpm db:check` | Migration journal consistency **and** drift: fails, printing the SQL, if `src/schema` has changes without a migration. |
| `pnpm db:seed [--only a,b] [--env dev\|test\|staging]` | Run idempotent seed modules (`src/seed/modules`). |
| `pnpm db:studio` | Drizzle Studio on `DATABASE_URL`. |
| `pnpm db:reset --yes` | Development only: drop everything, migrate, seed. Refuses when `NODE_ENV=production`. |

`DATABASE_URL` comes from `.env.generated` (written by `pnpm infra:up`), `.env` or the environment.

## Adding a table

1. Create `src/schema/<context>.ts` (one file per bounded context) and re-export it from `src/schema/index.ts`.
2. Use the helpers so every table looks the same:

   ```ts
   import { pgTable, text, index } from 'drizzle-orm/pg-core';
   import { geographyPoint, id, orgId, timestamps } from '../index.ts';

   export const businesses = pgTable(
     'businesses',
     {
       id: id(), // UUIDv7, generated by the app
       organizationId: orgId(),
       name: text().notNull(),
       location: geographyPoint(), // { lat, lng }
       ...timestamps(),
     },
     (t) => [index('idx_businesses__organization_id_name').on(t.organizationId, t.name)],
   );
   ```

   Property names are camelCase; the client and Drizzle Kit use `casing: 'snake_case'`, so columns are
   `organization_id`, `created_at`, … without repeating names.
3. `pnpm db:generate --name add_businesses`, review the SQL, and append anything Drizzle cannot express (see
   below) to the same file.
4. Commit schema + migration + `meta/` together. `pnpm db:check` must pass.

## Conventions

- Names follow `docs/conventions/coding-standards.md` §5: plural `snake_case` tables, `<entity>_id` foreign keys,
  `idx_<table>__<cols>`, `uq_<table>__<cols>`, `ck_<table>__<rule>`. Org-scoped tables lead their composite
  indexes with `organization_id`.
- **`updated_at`** is maintained by the database. After creating a table that has it, add:
  `CREATE TRIGGER trg_<table>__updated_at BEFORE UPDATE ON <table> FOR EACH ROW EXECUTE FUNCTION set_updated_at();`
- **Coordinates**: always `{ lat, lng }` in TypeScript. PostGIS and GeoJSON order them `lng, lat`; the custom
  types do the conversion so nobody else has to. Areas are GeoJSON `MultiPolygon` (a `Polygon` is promoted).
- **Embeddings**: `vector(dimensions)` checks the length and finiteness of every write.
- **Full-text**: generated `tsvector` columns use `bf_tsvector(text_en, text_fr, text_simple)`, which is
  accent-insensitive through the IMMUTABLE `f_unaccent()` wrapper (plain `unaccent()` cannot be indexed).
- **Raw SQL** is fine for what Drizzle cannot express (generated columns, partial/expression indexes, triggers,
  RLS, materialized views, hybrid search) — always through the `sql` tag with bound parameters, never string
  concatenation.

## Transactions (Unit of Work)

Use cases open the transaction; repositories never take a `tx` argument:

```ts
// application/use case
await runInTransaction(db, async () => {
  await businesses.save(business);
  await outbox.append(event);
});

// infrastructure/repository
async save(b: Business) {
  await getExecutor(this.db).insert(businesses).values(toRow(b));
}
```

Nested `runInTransaction` calls join the outer transaction; `{ savepoint: true }` isolates a nested step whose
failure you intend to catch. `isolationLevel` can only be set on the outermost call.

## Migrations: forward-only, safe on populated tables

- Never edit a migration that has been merged. Fix forward with a new one.
- No long exclusive locks on large tables. Create indexes concurrently, **alone in their own migration** (Drizzle
  runs each migration in a transaction, and `CREATE INDEX CONCURRENTLY` cannot run inside one):

  ```sql
  -- 0012_idx_businesses_name_trgm.sql (hand-written, drizzle-kit generate --custom)
  CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_businesses__name_trgm ON businesses USING gin (name gin_trgm_ops);
  ```

  Mark such a migration in its PR; deploy runs it outside a transaction (BF-025).
- Adding a `NOT NULL` column: add it nullable (or with a constant default), backfill, then set `NOT NULL` — or
  add a `CHECK (…) NOT VALID` constraint and `VALIDATE CONSTRAINT` in a later migration.

### Expand / contract (renames, type changes, splits)

1. **Expand** (PR 1): add the new column/table; the app writes both old and new, reads old.
2. **Migrate** (PR 2 or a job): backfill new from old in batches; switch reads to new.
3. **Contract** (PR 3, after a deploy cycle): stop writing old; drop it.

Each step is deployable and reversible on its own; never combine expand and contract in one release.

## Tests

- Unit tests (`*.test.ts`) need no database.
- Integration tests (`*.int.test.ts`, `pnpm test:int`) use `@bf/testing/db`: one Postgres container from
  `infra/docker/postgres` per run (or `BF_TEST_PG_IMAGE`), migrated once into a template; each test file gets a
  clone via `createIsolatedDatabase()`. `withRollback(db, fn)` (`src/testing.ts`) wraps single-connection tests in
  a transaction that is always rolled back; `truncateAll(url)` empties tables for multi-connection tests.
